.# Abstract

This document specifies two block Forward Error Correction (FEC) schemes
for the FEC mechanism of Media over QUIC (MoQ): the systematic
Reed-Solomon erasure code over GF(2^8) of ISO/IEC 23008-10, which is
mandatory to implement, and RaptorQ (RFC 6330), which is optional.  For
each scheme it gives the registered identifier, the derivation of the
decoder's parameters from the instance's configuration and the Repair
FEC Payload ID with no in-session signaling, the bounds on block size
and symbol size, the decoding overhead, and how the scheme supports
repair layers.  It restates the Reed-Solomon code and gives test vectors
for it.

{mainmatter}

{#introduction}
# Introduction

[@!MOQ-FEC-CORE] specifies how FEC repair data is carried alongside
source media in MoQ without naming an FEC code.  Its Section
4.2 states the properties that a
block FEC scheme must have to be used with that mechanism, and the
information that a scheme's specification must give.  This document
specifies two such schemes: the systematic Reed-Solomon erasure code
over GF(2^8) of [@!ISO.23008-10], which is mandatory to implement, and
RaptorQ [@!RFC6330], which is optional.  For each it gives the scheme
identifier ((#scheme-identifiers)), the derivation of the decoder's
parameters ((#reed-solomon), (#raptorq)), the bounds the scheme imposes
on a configuration and on a repair object ((#scheme-bounds)), how its
repair symbols are numbered and generated ((#repair-symbols)) and how it
supports repair layers ((#repair-layers)).  For Reed-Solomon it also
restates the code ((#rs-code)), because [@!ISO.23008-10] is not freely
available, and gives test vectors ((#test-vectors)).

{#conventions-and-definitions}
# Conventions and Definitions

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
"SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
"OPTIONAL" in this document are to be interpreted as described in BCP 14
[@!RFC2119] [@!RFC8174] when, and only when, they appear in all
capitals, as shown here.

This document uses the terms of [@!MOQ-FEC-CORE] Section
2.  The ones it relies on are
restated here; the others are as that section defines them.

**FEC Instance**: One independent FEC encoding over a sequence of source
symbols, with its own source symbol bound K, symbol size T, SS_ID space,
block partition, repair symbols and repair tracks.  A source track has
one or more FEC instances ([@!MOQ-FEC-CORE] Section
5.1).

**Source Symbol**: A T-byte unit of source data that an FEC instance
encodes.  Source symbols are formed from source objects by the
instance's block profile ([@!MOQ-FEC-CORE] Section
5.2).

**Repair Symbol**: A T-byte unit generated by the FEC scheme from the
source symbols of one block.

**SS_ID**: The 32-bit sequence number of a source symbol within its FEC
instance.  It wraps modulo 2^32 ([@!MOQ-FEC-CORE] Section
7.6).

**Source Block**: A run of SSB_length consecutive source symbols, 1 <=
SSB_length <= K, over which a block FEC scheme encodes.  A block is the
SS_ID range [SS_Start, SS_Start + SSB_length) and is identified by its
SS_Start.

**SS_Start and SSB_length**: The first SS_ID of a source block and the
block's source symbol count, carried in the Repair FEC Payload ID of
every repair object of the block ([@!MOQ-FEC-CORE] Section
7.5).

**FEC Block**: The combination of SSB_length source symbols and P repair
symbols; the ISO encoding symbol block ([@?ISO.23008-1] 3.1.5).

**Encoding Symbol ID (ESI)**: The index of a symbol within its block: a
source symbol's serial distance from SS_Start, and SSB_length + RS_ID
for a repair symbol.

**RS_ID**: The zero-based index of a repair symbol among the repair
symbols of its block.

**RSB_length**: The number of repair symbols generated for a block, the
instance's total repair count P when the block's repair symbols are
generated, carried in the Repair FEC Payload ID of every repair object
of the block ([@!MOQ-FEC-CORE] Section 7.5).

**Repair Layer**: One of possibly several repair tracks of one FEC
instance, each carrying a disjoint range of RS_IDs for every block
([@!MOQ-FEC-CORE] Section 7.3).  Layer 0 is the base
layer.

**RS_ID Offset**: The first Repair Symbol ID a layer may use; O_i for
layer i ([@!MOQ-FEC-CORE] Section 7.3.1).

**Object Transmission Information (OTI)**: Parameters required to
configure a RaptorQ decoder, as defined in [@!RFC6330].

**Block Profile**: The rules that fix how source symbols are formed from
source objects and how blocks are delimited and identified
([@!MOQ-FEC-CORE] Section
5.2).

K, P and T denote an instance's `sourceSymbols`, its total repair count
over all its repair layers, and its `symbolSize` ([@!MOQ-FEC-CORE]
Section 10.1); P_i is the repair count of layer
i.

{#scheme-identifiers}
# Scheme Identifiers

FEC scheme identifiers are registered in the "MoQ FEC Schemes" registry
([@!MOQ-FEC-CORE] Section 15.2); the scheme
parameter of an FEC instance ([@!MOQ-FEC-CORE] Section
10.1) carries the string identifier, and the
catalog binding encodes it ([@?MOQ-FEC-CATALOG] Section
3.1).  This document defines two:

**"raptorq"**: RaptorQ fountain code per [@!RFC6330].  Can recover from
loss of any symbols as long as SSB_length symbols (source or repair),
plus a small decoding overhead ((#repair-layers)), are received.  It is
OPTIONAL ((#mandatory-to-implement)).

**"reed-solomon"**: The systematic Reed-Solomon erasure code over
GF(2^8) of [@!ISO.23008-10] Clause 6, restated in (#rs-code).  It
recovers a block from any SSB_length of its distinct source and repair
symbols.  An FEC instance under it holds at most 255 source and repair
symbols per block ((#scheme-bounds)).  It is the mandatory-to-implement
scheme ((#mandatory-to-implement)).

Both codes are systematic: the source symbols of a block are among its
encoding symbols, so a receiver uses the source symbols it receives as
they arrive.  The two identifiers correspond to the FEC code points 3
(the "6330 code") and 1 (the RS code) of [@!ISO.23008-10] Table 1, which
an AL-FEC message carries in `fec_code_id_for_repair_flow` ([@?MOQ-MMT]
Section 8.3).

{#core-requirements}
# Requirements of the Core Met by These Schemes

[@!MOQ-FEC-CORE] Section 4.2 lists
eight properties that a block scheme must have and that its
specification must establish.  This section states, for each, where this
document establishes it for "reed-solomon" and for "raptorq".

1. **Erasure code.** "reed-solomon" recovers a block from any SSB_length
   of its distinct source and repair symbols ((#rs-code)).  "raptorq"
   can recover from loss of any symbols as long as SSB_length symbols
   (source or repair), plus a small decoding overhead, are received
   ([@!RFC6330]; (#repair-layers)).

2. **Systematic.** Both codes are systematic: the source symbols of a
   block are among its encoding symbols, so a receiver uses the source
   symbols it receives as they arrive ((#scheme-identifiers)).  Under
   "reed-solomon" the source symbols themselves are sent unchanged
   ((#rs-code)); under "raptorq" they occupy ESIs 0 to SSB_length - 1 of
   the [@!RFC6330] source block ((#repair-symbols)).

3. **Fixed symbol size.** Under both schemes every source and repair
   symbol is exactly T bytes.  "raptorq" requires T to be a multiple of
   8, the Symbol Alignment of its derived OTI ((#raptorq-oti));
   "reed-solomon" imposes no alignment ((#rs-parameters)).

4. **Index-fixed repair.** Under either scheme, a repair symbol is fixed
   by its block and its RS_ID alone, whichever layer carries it: RaptorQ
   through its open Encoding Symbol ID space, and the Reed-Solomon code
   of this document through a Cauchy generator matrix whose column j
   depends on RS_ID j alone ((#repair-layers)).

5. **Parameters from configuration and the wire.** Under both schemes
   the decoder of each block is configured from the instance's
   configuration and the block's Repair FEC Payload ID, and no other
   signaling is defined: (#raptorq-oti) derives the RaptorQ OTI, and
   (#rs-parameters) the Reed-Solomon parameters.

6. **Stated bounds.** (#scheme-bounds) states, for each scheme, the
   largest K, the largest SSB_length + RSB_length and the largest RS_ID,
   and the constraint on T.

7. **Stated recovery condition.** The decoding overhead e is 0 under
   "reed-solomon", which is maximum distance separable, and under
   "raptorq" a small number of symbols with the residual failure
   probabilities of [@!RFC6330] ((#repair-layers)).

8. **Deterministic and verifiable.** Both codes are deterministic:
   (#rs-code) fixes the field, the generator matrix and the order of
   symbols, and [@!RFC6330] fixes every table and index of RaptorQ.
   (#test-vectors) gives test vectors that tell the Reed-Solomon
   construction of this document apart from other systematic
   Reed-Solomon constructions over GF(2^8).  (#raptorq-test-vectors)
   gives RaptorQ test vectors that fix, for a block of this document,
   the OTI that (#raptorq-oti) derives and the Encoding Symbol ID that
   (#repair-symbols) gives each RS_ID.

Both schemes support repair layers ((#repair-layers)), which
[@!MOQ-FEC-CORE] Section 4.2 asks a
scheme specification to state.  "reed-solomon" is maximum distance
separable; "raptorq" is not, but is close to it at every block size of
(#scheme-bounds).  (#security-considerations) states the decoding cost
of "reed-solomon" and, for "raptorq", points at the decoder of
[@!RFC6330].

{#reed-solomon}
# Reed-Solomon

{#rs-code}
## The Code

The "reed-solomon" scheme is the systematic Reed-Solomon erasure code
over GF(2^8) of [@!ISO.23008-10] Clause 6, to which that document
assigns FEC code point 1 (its Table 1).  This section restates the code,
because [@!ISO.23008-10] is not freely available.  If this restatement
and [@!ISO.23008-10] Clause 6 differ, [@!ISO.23008-10] governs.
(#test-vectors) gives test vectors.

**Field.** The code works in GF(2^8) defined by the primitive polynomial
x^8 + x^4 + x^3 + x^2 + 1 (0x11D), the polynomial that [@?RFC5510]
Section 8.1 gives for m = 8.  alpha is a root of that polynomial and is
represented by the byte 0x02.  A byte with bits b_7 (the most
significant) down to b_0 represents the element b_7 alpha^7 + b_6
alpha^6 + ... + b_1 alpha + b_0.  Addition is the bitwise exclusive OR
of bytes, and multiplication is the product of polynomials modulo 0x11D,
so alpha^8 is 0x1D.  This document defines the code over GF(2^8) only.

**Generator matrix.** The code is generated by G = [I | A], where I is
an identity matrix and A is a Cauchy matrix ([@!ISO.23008-10] Clause 6.2
writes G = [I; A]).  Row i of A belongs to the source symbol at ESI i,
and column j to the repair symbol whose RS_ID is j.  The entries of A
are:

~~~
A_{i,j} = 1 / (x_i + y_j)
x_i     = alpha^(254 - i)
y_j     = alpha^j
~~~

A block that holds SSB_length source symbols and RSB_length repair
symbols uses rows 0 to SSB_length - 1 and columns 0 to RSB_length - 1 of
A.  x_i and y_j differ whenever i + j < 254, so every entry the block
uses is defined when SSB_length + RSB_length is at most 255, the bound
of [@!ISO.23008-10] Clause 6.2.  An entry depends on i and j alone: not
on K, not on SSB_length and not on P.

**Encoding.** Every symbol of a block is T bytes long.  Let s_i be the
source symbol at ESI i ([@!MOQ-FEC-CORE] Section
5.5), for i from 0 to SSB_length - 1.  The
repair symbol r_j whose RS_ID is j is computed one byte position at a
time, as [@?RFC5510] Section 8.4 applies its code to symbols: for each
byte position u from 0 to T - 1,

~~~
r_j[u] = sum over i < SSB_length of A_{i,j} * s_i[u]
~~~

where the sum and the products are computed in GF(2^8).  The source
symbols themselves are sent unchanged.

**Short blocks.** A block whose SSB_length is less than K uses only the
first SSB_length rows of A.  Its repair symbols equal those of a block
of K source symbols whose symbols at ESIs SSB_length to K - 1 are all
zero, because a zero symbol adds nothing to any sum.  No zero symbol is
sent or counted in SSB_length ([@!MOQ-FEC-CORE] Section
5.4).

**Decoding.** Every square submatrix of a Cauchy matrix is invertible
([@!ISO.23008-10] Clause 6.2), so the code is maximum distance
separable: a receiver that holds any SSB_length distinct symbols of a
block, source and repair in any mix, recovers every source symbol of the
block.  Let M be the set of ESIs of the source symbols it lacks, and R a
set of |M| RS_IDs of repair symbols that it holds.  For each byte
position u and each j in R:

~~~
sum over i in M of A_{i,j} * s_i[u]
    = r_j[u] + sum over i < SSB_length, i not in M,
               of A_{i,j} * s_i[u]
~~~

The square matrix of the entries A_{i,j} with i in M and j in R is a
submatrix of A and is therefore invertible.  The receiver inverts it
once per block and applies the result at every byte position.  Any
decoding method that yields the same source symbols is acceptable.

The field is that of [@?RFC5510], but the generator matrix is not the
Vandermonde-derived matrix of [@?RFC5510] Section 8.2, and this document
uses neither the FEC Payload IDs nor the source block partitioning of
[@?RFC5510].  Several systematic Reed-Solomon constructions over GF(2^8)
are in use, and they produce different repair symbols from the same
source symbols.  (#test-vectors) gives test vectors that tell this
construction apart from the others.

{#rs-parameters}
## Parameters

As for RaptorQ ((#raptorq-oti)), no decoder configuration is carried on
the wire, and the code has no OTI to carry.  When an instance's scheme
is "reed-solomon", receivers MUST configure the decoder of each FEC
block from the instance's configuration ([@!MOQ-FEC-CORE] Section
10.1) and the block's Repair FEC Payload ID
([@!MOQ-FEC-CORE] Section 7.5), under the
source symbol construction of the instance's block profile
([@!MOQ-FEC-CORE] Section
5.2), as follows:

- **Symbol size**: T = `symbolSize`.  Every source and repair symbol is
  exactly T bytes.  The RaptorQ rule that T is a multiple of 8
  ((#raptorq-oti)) does not apply.
- **Rows**: SSB_length, the block's source symbol count.  The source
  symbol whose SS_ID is x is row (x - SS_Start) mod 2^32 of A, which is
  its ESI ([@!MOQ-FEC-CORE] Section 5.5).
- **Columns**: the repair symbol whose RS_ID is j is column j of A.  Its
  ESI, SSB_length + RS_ID ((#repair-symbols)), still identifies it
  within its block, but the column depends on RS_ID alone.
- **Column count**: RSB_length, the instance's total repair count P
  ([@!MOQ-FEC-CORE] Section 7.5).

This derivation is normative and complete: a receiver that has an
instance's configuration requires no additional signaling to configure
its decoder ([@!MOQ-FEC-CORE] Section
4.2, requirement 5).  As under
RaptorQ, its per-block inputs travel in the Repair FEC Payload ID of
every repair object of the block.

The configuration keeps every FEC instance under "reed-solomon" within
the bound of (#rs-code): K + P is at most 255, where K is the instance's
`sourceSymbols` and P its total repair count over all its repair layers
((#scheme-bounds)).  SSB_length + RSB_length is then at most 255 in
every block.  In addition to the checks of [@!MOQ-FEC-CORE] Section
5.4, a receiver MUST discard a repair
object of such an instance whose SSB_length + RSB_length exceeds 255, or
whose RS_ID is not less than RSB_length, leaving the state of every
block unchanged.  Neither object carries a symbol of a code that
(#rs-code) defines.  A repair object whose RSB_length is less than O_i +
P_i for a layer i that the receiver holds goes to one of two rules.
When the object is on that layer's own track, i above 0, or belongs to
a block to which the check of [@!MOQ-FEC-CORE] Section
7.3.2 applies, that check handles it: it
fails closed and stops FEC for the instance.  Otherwise this rule
applies, and the receiver discards the object only if it breaks one of
the two conditions above.  Such an object is one of a block generated
before an append, carrying no symbol of layer i, or one of layer 0's
track generated under a previous total ([@!MOQ-FEC-CORE] Section
7.3.2).

Repair layers ([@!MOQ-FEC-CORE] Section 7.3) carry
disjoint ranges of columns: layer i carries columns O_i to O_i + P_i - 1
([@!MOQ-FEC-CORE] Section 7.3.1).  A column
depends on its RS_ID alone, so a repair symbol is the same whichever
layer carries it and whatever other layers exist, and symbols from any
subset of layers combine in one decode.  Each FEC instance of a source
track, including an instance that overlaps another ([@!MOQ-FEC-CORE]
Section 8.4), has its own rows, numbered from
its own SS_IDs, its own columns and its own bound: K + P is at most 255
in each instance, whatever another instance of the track uses.

For example, this configuration, shown in the shape of the catalog
binding ([@?MOQ-FEC-CATALOG]), protects a LOC video track under
"reed-solomon":

~~~ json
{
  "version": 1,
  "tracks": [
    {
      "name": "video",
      "packaging": "loc",
      "isLive": true,
      "codec": "avc1.64001f",
      "width": 1280,
      "height": 720,
      "framerate": 30,
      "bitrate": 2500000,
      "fec": [
        {
          "instanceId": 0,
          "scheme": "reed-solomon",
          "blockProfile": "moq-object-v1",
          "sourceSymbols": 32,
          "repairSymbols": 8,
          "symbolSize": 1320,
          "interleaveDepthMs": 200,
          "reorderToleranceMs": 40,
          "repairTrack": "video/repair"
        }
      ]
    },
    {
      "name": "video/repair",
      "packaging": "fec-repair",
      "isLive": true,
      "source": "video",
      "instanceId": 0,
      "repairLayer": 0,
      "repairSymbols": 8,
      "priority": 240
    }
  ]
}
~~~

K + P is 32 + 8 = 40, within the bound.  A full block uses rows 0 to 31
and columns 0 to 7 of A, and its repair objects carry SSB_length 32 and
RSB_length 8.  A short block of 20 source symbols uses rows 0 to 19 and
the same columns, and its repair objects carry SSB_length 20.  The
repair symbol with RS_ID 3 is column 3 in both blocks, at ESI 35 in the
first and ESI 23 in the second.  The full block recovers once the
receiver holds any 32 of its 40 symbols, and the short block once it
holds any 20 of its 28.  The bound of (#scheme-bounds) leaves room for
repair layers ([@!MOQ-FEC-CORE] Section 7.3.2)
of at most 215 more repair symbols in all, since 32 + 8 + 215 = 255, and
[@!MOQ-FEC-CORE] Section 14.4 recommends far fewer.

{#raptorq}
# RaptorQ

{#raptorq-oti}
## Object Transmission Information

An RFC 6330 decoder is configured by the Object Transmission Information
(OTI): the 8-byte Common FEC OTI (Section 3.3.2 of [@!RFC6330]) and the
4-byte Scheme-Specific FEC OTI (Section 3.3.3 of [@!RFC6330]), totaling
12 bytes:

~~~
RaptorQ OTI {
  Transfer Length (40),
  Reserved (8),
  Symbol Size (16),
  Number of Source Blocks (8),
  Number of Sub-Blocks (16),
  Symbol Alignment (8),
}
~~~

This specification does not carry the OTI on the wire.  When an
instance's scheme is "raptorq", receivers MUST construct the OTI of each
FEC block from the instance's configuration ([@!MOQ-FEC-CORE] Section
10.1) and the block's SSB_length, which every
repair object of the block carries ([@!MOQ-FEC-CORE] Section
7.5), under the source symbol construction of
the instance's block profile ([@!MOQ-FEC-CORE] Section
5.2), as follows:

- **Transfer Length**: F = SSB_length x T, where SSB_length is the
  block's source symbol count and T is `symbolSize`, exact because every
  source symbol of a block profile is exactly T bytes.  It is never
  computed from the cumulative size of source objects, which a receiver
  that has lost objects could not know, and never from `sourceSymbols`,
  which bounds SSB_length but is not the size of any particular block
  ([@!MOQ-FEC-CORE] Section 5.4).  From
  this F an [@!RFC6330] decoder derives that document's K as SSB_length,
  and from K its own K' ([@!RFC6330] Section 5.3.1).
- **Symbol Size**: T = `symbolSize`.
- **Number of Source Blocks**: Z = 1.  Each FEC block is decoded as an
  independent RFC 6330 object containing a single source block.  Blocks
  are identified by the SS_Start of the Repair FEC Payload ID of repair
  objects, and source symbols are placed in them by SS_ID
  ([@!MOQ-FEC-CORE] Section 5.5) -- not by
  the RFC 6330 Z partitioning.
- **Number of Sub-Blocks**: N = 1.  Sub-blocking is not used; the MMTP
  block profile states the same for its sub-block mode ([@?MOQ-MMT]
  Section 7.1).
- **Symbol Alignment**: Al = 8.  `symbolSize` MUST be a multiple of 8
  ((#scheme-bounds)).

This derivation is normative and complete: a receiver that has an
instance's configuration requires no additional signaling to configure
its decoder ([@!MOQ-FEC-CORE] Section
4.2, requirement 5).  Its one
per-block input, SSB_length, travels in the Repair FEC Payload ID of
every repair object of the block, so a receiver holding any repair
symbol of a block holds the block's SSB_length.

Under "raptorq", a block of SSB_length source symbols is an [@!RFC6330]
source block whose K, in the notation of [@!RFC6330], is SSB_length; the
K of [@!MOQ-FEC-CORE] is the configured bound instead.  The extension of
that source block to K' symbols by padding ([@!RFC6330] Section 5.3.1)
happens inside the encoder and the decoder and is not visible on the
wire, and this document defines no K' of its own.

The Symbol Alignment does not affect the symbols.  In [@!RFC6330] Al
governs only the division of a symbol into sub-symbols across the N
sub-blocks (its Section 4.4.1.2), and with N = 1 every symbol is one
contiguous run of T bytes whatever Al is.  A library that fixes Al at
another value, such as 1, therefore produces the same source and repair
symbols for the same F, T and K, and conforms to this document; the Al
= 8 of the derived OTI records that `symbolSize` is a multiple of 8
((#scheme-bounds)), and nothing else depends on it.

For example, for an instance with K = 32 and T = 1312, a full block
(SSB_length = K = 32) has Transfer Length F = SSB_length x T = 32 x 1312
= 41,984 bytes, Symbol Size T = 1312, Z = 1, N = 1, Al = 8.  No
in-session message is required.

{#scheme-bounds}
# Scheme Bounds

[@!MOQ-FEC-CORE] Section 4.2,
requirement 6, asks a scheme to state the largest K, the largest
SSB_length + RSB_length and the largest RS_ID that its construction
supports, and [@!MOQ-FEC-CORE] Section 10.3 applies those
bounds to a configuration before FEC starts.  This section is the one
place that states them for the two schemes of this document.  A receiver
rejects a configuration, and discards a repair object, outside them
([@!MOQ-FEC-CORE] Sections 10.3 and
7.5).

Under "reed-solomon":

- K + P is at most 255 for each FEC instance: its `sourceSymbols` plus
  the `repairSymbols` of all its repair layers.  Every entry of A that a
  block of the instance uses is then defined ((#rs-code)).  SSB_length +
  RSB_length is therefore at most 255 in every block, and the largest
  RS_ID, RSB_length - 1, is at most 253.
- A publisher that appends a repair layer MUST keep the instance within
  this bound with the new total ([@!MOQ-FEC-CORE] Section
  7.3.2).
- T is at least 1, and no alignment applies ((#rs-parameters)).

Under "raptorq":

- K is at most 56403 for each FEC instance.  [@!RFC6330] extends a
  source block of K source symbols to K' symbols, the smallest value at
  least K in its Table 2 ([@!RFC6330] Section 5.3.1), and 56403 is the
  largest such value, K'_max ([@!RFC6330] Section 5.1.2), so a RaptorQ
  source block holds at most 56403 source symbols.
- `symbolSize` is a multiple of 8, the fixed Symbol Alignment of the
  derived OTI ((#raptorq-oti)), so the least T this scheme admits is 8.
  A block profile can place a larger floor on T, as the MMTP block
  profile does ([@?MOQ-MMT] Section 7.1); that floor
  is the profile's rule, not a bound of this scheme, and under it the
  least T is the smallest multiple of 8 at or above the floor.  A
  RaptorQ symbol size off the Symbol Alignment fits no derived OTI.
- The largest Encoding Symbol ID of [@!RFC6330] is 2^24 - 1 (its Section
  3.2), the bound that [@!MOQ-FEC-CORE] Section 10.3
  already places on K + P - 1 for every scheme, so "raptorq" adds no
  bound of its own on SSB_length + RSB_length or on RS_ID.

{#repair-layers}
# Repair Layers

Both schemes support repair layers ([@!MOQ-FEC-CORE] Section
7.3).  Layering needs a code whose repair symbols are
identified by ESI alone and whose repair symbol for a given ESI does not
depend on how many repair symbols the block generates in total.  Only
then do repair symbols from disjoint ESI ranges on separate tracks
remain symbols of one code, and only then can a receiver add a layer
without the publisher re-encoding.  RaptorQ has this property by
construction, through its open Encoding Symbol ID space ([@!RFC6330]).
The property is not particular to fountain codes.  A systematic
Reed-Solomon code whose generator matrix is Vandermonde-derived
([@?RFC5510] Section 8.2.1) or Cauchy-derived has it too, provided the
field element that defines each repair column is fixed by the symbol's
index in the code and never by P.  [@?RFC5510] fixes it as alpha^j for
the Encoding Symbol ID j, so a repair column is fixed by SSB_length and
RS_ID together, through ESI = SSB_length + RS_ID.  The Cauchy
construction of (#rs-code) fixes y_j as alpha^j for RS_ID j, so a repair
column is fixed by RS_ID alone.  Each repair symbol is then one fixed
column of that matrix, independent of the code length n = K + P, and the
field size is the only bound: K + P is at most 2^m - 1 over GF(2^m) for
the [@?RFC5510] construction, and at most 2^m for a Cauchy construction
in general.  The construction of (#rs-code), whose x_i and y_j are
nonzero powers of alpha, allows 2^m - 1, that is 255.  A Reed-Solomon
code in generator-polynomial form lacks the property: its parity is the
remainder modulo a polynomial of degree n - K, so its symbols for one P
are not valid for another.

The "reed-solomon" code of (#rs-code) meets the conditions of
[@!MOQ-FEC-CORE] Section 4.2 for a
scheme that supports layers: column j of A depends on RS_ID j alone,
through y_j = alpha^j, and not on P or on SSB_length; layer i carries
columns O_i to O_i + P_i - 1 ((#rs-parameters)); and (#scheme-bounds)
bounds K + P by 255 for each FEC instance.  Under "raptorq", layer i
carries, for every block, the repair symbols whose Encoding Symbol IDs
are SSB_length + O_i to SSB_length + O_i + P_i - 1 of the block's
[@!RFC6330] source block ((#repair-symbols)), and (#scheme-bounds)
bounds K.

A receiver that has subscribed a set of layers recovers a block whenever
the number of lost symbols, source and repair together, does not exceed
C - e, where C is the total P over the layers it holds and e is the
decoding overhead of the instance's scheme: 0 under "reed-solomon",
which is maximum distance separable ((#rs-code)), and under "raptorq" a
small number of symbols (roughly 1e-2, 1e-4, and 1e-6 residual failure
at 0, 1, and 2 symbols of overhead per [@!RFC6330]).

{#repair-symbols}
# Repair Symbols

For RaptorQ, repair symbols are generated per [@!RFC6330] Section 5.3.
The source symbols of a block occupy ESIs 0 to SSB_length - 1 in SS_ID
order, and the Encoding Symbol ID (ESI) of a repair symbol starts at
SSB_length, the block's K in the notation of [@!RFC6330] ([@!RFC6330]
Section 5.3.1): ESI = SSB_length + RS_ID, both fields taken from the
Repair FEC Payload ID ([@!MOQ-FEC-CORE] Section
7.5).  The Internal Symbol IDs of [@!RFC6330],
which start the repair symbols at that document's K', are internal to
its encoder and decoder and never appear on the wire.

For Reed-Solomon, repair symbols are generated per (#rs-code).  Source
and repair symbols carry the same ESIs as under RaptorQ, so ESI =
SSB_length + RS_ID still identifies a repair symbol within its block,
but the code takes the symbol's column of A from its RS_ID alone
((#rs-parameters)).

Under "raptorq" the block is a RaptorQ source block of SSB_length source
symbols, whose decoder is configured with F = SSB_length x T
((#raptorq-oti)); under "reed-solomon" SSB_length is the number of rows
of A that the block uses ((#rs-parameters)).

A short source block ([@!MOQ-FEC-CORE] Section
5.4) is encoded as a block of its
SSB_length source symbols, at ESIs 0 to SSB_length - 1 in SS_ID order:
under "raptorq" a RaptorQ source block with F = SSB_length x T
((#raptorq-oti)), and under "reed-solomon" the first SSB_length rows of
A ((#rs-code)).  No padding symbol is transmitted, and none is counted
in SSB_length or F.  The padding of the block to K' symbols in the
notation of [@!RFC6330] ([@!RFC6330] Section 5.3.1) is part of RaptorQ
encoding and decoding, performed inside the encoder and the decoder.  A
short block is recoverable once the source and repair symbols the
receiver holds together number at least SSB_length, plus the decoding
overhead of (#repair-layers), which is zero under "reed-solomon".

{#mandatory-to-implement}
# Mandatory-to-Implement Scheme

Reed-Solomon is the mandatory-to-implement FEC scheme: an implementation
that performs FEC decoding under [@!MOQ-FEC-CORE] MUST support
"reed-solomon", which (#reed-solomon) fully specifies.  "raptorq" is
OPTIONAL.

The MMT AL-FEC framework on which the MMTP block profile of [@?MOQ-MMT]
rests ([@?ISO.23008-1] Annex C) requires no FEC code: it carries
whichever code the AL-FEC message names by its [@!ISO.23008-10] code
point, and ATSC 3.0, which applies AL-FEC to an MMTP session through
that framework, requires none either ([@?ATSC-A331] Section 8.1.2.5;
[@?MOQ-MMT] Section 10).  This document
therefore specifies the codes it uses.  Reed-Solomon is the mandatory
scheme because it is small to implement, recovers a block from exactly
SSB_length of its symbols, and is a code of that framework
([@!ISO.23008-10] code point 1).  RaptorQ stays specified, code point 3,
for its block size: it serves every block size this document allows.
A RaptorQ block holds up to 56403 source symbols ((#scheme-bounds)),
while a Reed-Solomon block holds at most 255 source and repair symbols.
At 8 Mb/s with symbols of 1200 bytes, 255 symbols are about 300 ms,
and a Reed-Solomon block's 255 - P source symbols span less than that,
so the multi-second interleave windows of
[@!MOQ-FEC-CORE] Section 9.3 need RaptorQ
at that rate.

A receiver that does not implement the scheme of an FEC instance forgoes
FEC for that instance, as [@!MOQ-FEC-CORE] Section
4.5 specifies; an instance under "raptorq" is
therefore protected only for the receivers that implement it.

{#security-considerations}
# Security Considerations

The security considerations of [@!MOQ-FEC-CORE] apply.  [@!MOQ-FEC-CORE]
Section 14.3 bounds a receiver's work per
instance; this section gives the Reed-Solomon figures.  Under "raptorq"
the cost of decoding a block is that of an [@!RFC6330] decoder for a
source block of SSB_length symbols of T bytes ((#raptorq-oti)), which
[@!RFC6330] Section 5.4 describes; this document gives no closer
figure.

The configuration bounds the cost of "reed-solomon" decoding.  A block
has at most 255 source and repair symbols ((#scheme-bounds)), so the
number of source symbols a receiver recovers in it, E, is at most
min(SSB_length, RSB_length), which is at most 127.  The receiver inverts
one E x E matrix per block and performs about E x SSB_length x T
multiplications in GF(2^8) to form and apply the result ((#rs-code)).
One open block holds at most 255 x T bytes of symbols.

The code provides no integrity protection, as RaptorQ provides none
([@!MOQ-FEC-CORE] Section 14.2).  A decoder that is given
a corrupted or injected symbol yields wrong source symbols and reports
no error, and when it decodes from exactly SSB_length symbols the code
itself cannot reveal the error.  The checks of the block profile
([@!MOQ-FEC-CORE] Section 9.2 for
"moq-object-v1", and [@?MOQ-MMT] Section 7.1 for MMTP
packets) reject some wrong results.  A receiver that holds more than
SSB_length symbols of a block can also re-encode the recovered block and
compare the result with the symbols it did not use: a mismatch shows
that some symbol it holds is not what the publisher encoded.

# Reed-Solomon Test Vectors

This appendix is informative.  It gives values of the `reed-solomon`
code of (#rs-code), so that an implementation can check its field
arithmetic, its matrix A and the order of its symbols.  Bytes are in
hexadecimal, and a symbol is written as its T bytes in order.  Two
separate implementations of (#rs-code) computed these values.  They have
not been checked against an implementation of [@!ISO.23008-10].

The field.  The powers of alpha fix the polynomial (alpha^8 = 1d) and
the representation of elements as bytes (alpha^7 = 80):
